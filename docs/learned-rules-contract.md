# learned 规则来源与兼容边界

规则摘要用于拒绝程序、表或配置不同的训练/推理组合。它不证明离线场景与竞技场的初始化、行动限制或资源恢复完全相同，也不证明模型具备相应策略能力。

## 实际输入

`prepare-battle-rules.sh` 在 GMSV 的工作目录调用同一个可执行文件的 `--battle-rules --config <文件>`。此入口只解析配置并导出白名单，不开启网络、加载账号或写角色存档。使用原生 `readconfigfile`，包括主机名后缀文件、空白处理、重复项、编译开关选择、原生缺省值、路径拼接及 getter 的范围限制。

摘要格式 `stoneage-native-rules-v2` 覆盖：

| 输入 | 来源与含义 |
| --- | --- |
| 引擎二进制 | 整个 `gmsvjt.exe` 的 SHA-256，包含战斗代码、编译选项、环境 adapter、竞技场规则常量及规则导出器 |
| 物品表 | `getItemfile()`；由实际启用的 itemset 配置项选择，并采用原生 `topdir` 前缀 |
| 宠物技能表 | `getPetskillfile()`；采用实际编译启用的 petskillfile1 或 petskillfile2 |
| 魔法与敌人表 | `getMagicfile()`、`getEnemyfile()`、`getEnemyBasefile()`；启用 `_ATTACK_MAGIC` 时另含 `getAttMagicfileName()` |
| 可选固定路径表 | 依据编译开关包含 `data/needitemeneny.txt`、`data/ride.txt`、`data/leaderride.txt`；缺失显式记录 `absent`，与空文件区分 |
| 经验表 | 启用 `_USER_EXP_CF` 时包含 `getEXPfile()` |
| 数值选项 | 按编译开关记录生效的 battleexp、skup、battlegold、ridemode、chartrans、pettrans、maxlevel、yblevel |

导出名称与配置键不必相同。例如 `battlegold` 来自大小写敏感的 `BATTLEGOLD`，`skup` 来自 `SKILLUPPOINT`。旧脚本直接按小写配置文本筛选会遗漏这些值。当前按实际 getter 导出，超出范围的值使用引擎相同的限制；未启用的编译分支不凭配置文本假定生效。

数值相同但字节不同的数据表会产生不同摘要，二进制中无关功能变化也可能改变摘要。这是保守的兼容校验，不承诺所有语义等价版本都得到同一摘要。原生解析器不能正常加载的表路径不会被脚本擅自正规化成另一个可读路径。

不把账号、密码、服务器地址、完整 setup.cf 或原始表路径存入规则归档。原生解析器输出的白名单路径只用于私有临时文件，归档前删除。正式归档仅包含表副本、数值选项和摘要清单；关闭战斗记录时也能只计算摘要，临时副本随后清理。

## 归档与运行时

完成的归档以摘要命名，多 worker 同时发布同一归档时复用获胜者，不把临时目录嵌套到归档内。复用前核验内容，缺文件、符号链接替代或数据损坏会失败，不返回可用摘要。归档只保存规则数据和二进制摘要，不复制可执行文件。

`BTRULES` 返回摘要与引擎平台，独立于 `BTIME`，不改变回合时间。服务端启动会重新计算摘要，训练 worker 也在每次启动前重新计算；不接受调用者随意提供的旧标签作为训练来源证明。

配置、物品、技能、魔法、敌人、骑乘及经验表的原生加载函数被再次调用时，启动摘要失效。即使重载失败也保守失效，因为全局表可能已经部分改变。服务端清除环境中的摘要，并向已登录客户端发出 `BTRULES||`，公共投影清除缓存元数据。learned 在当前场景明确回退；新排队前兼容检查失败。恢复有效摘要需要使用经过核验的资源重新启动服务；不会在重载后冒用旧值。

## 验证与剩余边界

`server/legacy/modern/tests/test-battle-rules-native.py` 使用实际编译的引擎验证主机专用配置、空白、重复项、默认值、范围限制、编译选择、路径前缀、可选文件、秘密隔离、并发发布和损坏归档拒绝；已纳入原生镜像的构建测试。原生竞技场 smoke 另外执行配置/宠物技能重载，并验证对双方客户端清除元数据且不改变截止时间。

当前覆盖审计针对现用 C 引擎的战斗表加载和上述配置。配点成长流程中的其他开关、地图/NPC/PVE 生成规则不以此表宣称全部覆盖；扩展相关训练场景时必须同步审核依赖并调整规则或场景版本。账号、配点、等级、装备、宠物实例及随机种子属于场景/观察，不使用此摘要替代记录。

离线环境按受控场景初始化表与资源；当前还覆盖状态攻击、两种治疗装备、小块肉、多宠切换和忠犬，未开放全部魔法与道具。即使它与竞技场的摘要相同，也必须完成同初始条件下的观察、动作效果和终局差分，才能声称该场景等价。在线等级 1 smoke 与离线等级 35 训练不构成这种差分证据。下文的 30 组为早期阶段记录，后续 120 组及忠犬独立场景的实际证据见 [实现记录](learned-implementation.md)。

`run-battle-parity.sh` 现已加入原生镜像构建检查：用同一套等级 35、120 点的人物/宠物及相同指令，分别执行真实训练 reset/step 和竞技场创建、邀请、准备、排队、入场、协议指令及结算。30 组覆盖 1v1～5v5、有宠/无宠、三个种子，其中一个为极端攻击/敏捷配置，验证击飞与主人离场时的宠物移除。逐回合比较槽位、存活和数值、原始 B 包、战斗随机调用数、终局，并验证竞技场恢复入场前受伤状态。已在现有本地 GCC 容器验证，远端镜像流水线尚未执行。

对照测试只为传输编码器单独提供随机流：原生 `util_EncodeMessage` 与战斗共用 libc `rand()`，有无真实连接会改变随机消耗。测试重新编译 `autil.c` 分离此流，战斗随机调用保持原样；不修改生产 RNG，也不据此宣称整个游戏服可由单一 seed 精确重放。

`TestNativeArenaProjectionParity` 读取上述两条路径捕获的 B/S 包，用正常客户端公共投影比较状态、候选、动作 mask、模型数值特征及历史摘要。只归一化会话/角色/宠物身份；所有非终局回合都必须成功编码，不再允许以相同拒绝代替覆盖。此前发现的多人击飞观察缺口已修复：原生竞技场及训练环境共用离场观战快照和电影补发，刚离场的回合不重复补发已有电影；编码器使用明确的成员映射，仅规划在场成员。完整范围仍限于这些受控场景，不代替复杂动作和胜率认证。

此次差分发现普通 PVP 的击飞后恢复 1 HP 及对离场成员重复接受指令不符合竞技场规则。训练环境现在复用竞技场的击飞处理、无 PVP 收益和行动菜单检查，场景升级为 `controlled-battle-v2`。旧 `--battle-dataset` 不启用此隔离环境范围；普通非竞技场游戏行为保留。v1 场景的 checkpoint/模型须重新采集训练，不能重标版本复用。

摘要在加载前计算，运行期间的磁盘编辑不会自动成为已加载规则；不得在计算摘要与加载之间并发修改资源。未来的动态资源机制若绕过已核查的加载函数，必须接入失效通知。规则格式此次升级后，旧模型、checkpoint 和历史测试保留原摘要；不手工重标为新规则，须新建实验重新采集训练。

## 训练镜像与游戏镜像

两者必须使用同一原生程序、表和有效参数。现用源码的 `__DATE__` / `__TIME__` 会进入二进制；独立构建若使用墙上时间，会使相同源码产生不同规则摘要。Docker 原生构建现使用 `SOURCE_DATE_EPOCH`，Release 统一传源码提交时间；手工构建未指定时为 0，不冒充某个 Release 的构建。旧本地产物及其摘要不重标。

Release 的 `training-compatibility` 检查从实际已构建镜像运行规则计算器，比较 ai-training 与 legacy-runtime 的 linux-amd64 默认规则摘要，相异时不发布 GitHub Release。ARM64 训练镜像用于同平台实验，不能修改模型平台字段去加载到 amd64 游戏服。这个检查只覆盖镜像默认配置，生产覆盖表/参数仍由现场 `BTRULES` 校验；镜像相同不等于现场规则一定相同。新流水线尚待实际 CI 执行，本地 GCC 编译时间验证不替代完整镜像比较。

## 受控宠物动作修复（controlled-battle-v3）

v3 设置原生合成宠物的技能槽容量，并通过公共 `S(AI)` 的 `active_pet` 刷新出战选择，修复过去宠物可能一直等待的问题。新增毒/石化/混乱/催眠技能；初始化核验真实表的 ID、处理函数、Field、Target 和精确选项字节，表不匹配时拒绝场景。原生对比重新覆盖 30 组，每个有宠场景须有宠物实际命中，每个人数模式须有状态电影；仅两条路径状态相同不再足够。新证据见实现记录，v2 及更早宠物实验不可用于当前策略强度判断。
