# learned 本地模型设计草案

状态：设计于 2026-09-29，经用户确认开始实施。基于 v0.2.9 代码核查；下文是完整目标，不代表所有功能已经完成。当前证据和未完成项见 [实现记录](learned-implementation.md)。

## 目标与边界

在给定竞技规则和资源条件下提高整队胜率。训练、推理、采集编排使用 Go，入口保留 `sactl ai`；现用 C 战斗引擎继续负责结算，不重写伤害、速度、状态和技能规则。每队一个指挥官，成员只负责观察、执行；保留 basic、learned、llm、hybrid。

两个独立但可迭代结合的学习问题：

- 配点：在严格相同预算和受控外部条件下选择整数属性分配。
- 作战：给定已经建立的角色和宠物，依据每回合己方共享信息与敌方公开信息，选择联合动作。

离线同点数实验和正式竞技场必须分开标记。当前竞技场使用角色及携带宠物的 power、积分和等待时间匹配，允许一定差距；不是严格等属性点数。`arena loadout` 目前是宠物携带掩码，不是重新配点接口。模型推荐不自动洗点，不调用管理端修改角色；是否新增公平配点赛制是另一项游戏设计。

## 模型架构：commander-policy-v2

选择一个可容纳 1v1～5v5 的小型集中式策略网络。第一阶段只训练并认证 1v1；支持变长输入不等于已经学会多人。

```text
各成员 battle-state + 截止当前观察的战斗事件
                    ↓
共同观察校验、己方视角归一化、可见性/缺失掩码
                    ↓
实体编码 → 两层关系注意力 → 战场表示 + 每个实体表示
                    ↓
历史摘要 GRU → 指挥官状态
               ↙              ↘
联合动作策略头                  局面价值头
依次规划人物/宠物指令             估计当前预期回报
               ↓
完整 Plan → 现有校验/截止时间/提交意图 → sactl 执行
```

### 输入

1. 参战实体：最多 20 个场上人物/宠物；HP、最大 HP、死亡/控制等已解析状态、阵营、人物/宠物类型、主人关系、具有游戏意义的位置。自己的属性、MP、装备、备用宠物、技能、物品资源另编码。背包及备用宠物不算成额外场上行动者。
2. 每个数值同时保留 known/missing 标记；未知不填成真实的 0，不凭服务器标签补齐敌方隐藏数值。数值采用有版本的缩放/对数变换，保留绝对量和比例，避免 HP 比例相同却实力悬殊被混同。
3. 候选动作：操作类型、执行实体、目标实体/群体、技能/道具可观察的效果类别、消耗、目标规则、数量及 ready。整数 ID 用作类别或关联键，不当连续强弱数值；名称和中文描述不是训练特征。
4. 历史：已发生的行动、伤害/恢复、控制变化、换宠、已知行动顺序和未知事件标记。仅到决策时间截点；本回合对手尚未公开的指令绝不进入输入。
5. 规则和模式：人数、预算场景、当前回合；规则摘要用于选模型和兼容校验。账号、姓名、角色稳定 ID、match_id 不进入网络，保留在执行和数据分组层。

先制作字段审计表：来源协议、CLI 字段、Web 战斗可见性、更新时点、缺失语义。复用公共投影，正常 Web 背包/宠物界面不增加编号。没有可信公开来源的技能效果保留 unknown，不能读取服务端私有状态来补模型输入。

受控场景的初始字段/缺失/动作/事件契约已落地，见 [特征契约](learned-feature-contract.md)。该实现明确保留未覆盖动作与历史汇总的局限，后续仍按本设计扩大覆盖。

### 推荐初始网络

| 模块 | 初始规格 | 作用 |
| --- | --- | --- |
| 实体/候选编码 | 两层 MLP，隐藏宽度 64 | 编码数值、类别及缺失标记 |
| 战场交互 | 2 层、4 头注意力，宽度 64，前馈宽度 128 | 表达角色、宠物及目标之间的关系 |
| 回合记忆 | GRU，隐藏宽度 64 | 累积已观察的对手行为与战况 |
| 计划状态 | 小型 GRU 或等价前缀编码，宽度 64 | 记录同回合已经规划的队友动作 |
| 动作评分头 | 共享 MLP，对当前实体各候选输出 logit | 变长候选 masked softmax |
| 价值头 | 战场/历史表示 → MLP → 标量 | 训练时评价行动前局面 |

目标控制在百万参数以内，具体数量随动作语义词表确定。默认 float32、CPU 训练/推理，无 GPU/Metal 依赖；不预先承诺训练耗时或推理延迟。实现后测真实 Mac 的批量训练吞吐和 5v5 推理 p50/p95。

Go 只实现所需的有限算子和反向传播，不建设通用深度学习框架。矩阵运算、softmax、注意力、GRU、Adam 的梯度检查及有限值检查是交付前提；梯度校验使用 float64。可替换数值后端，但不增加用户必须安装的 Python 环境。

### 联合动作如何形成

指挥官先看全队，再按有版本的规划顺序依次选择最多 10 个行动者的指令。每次选择都能看到全队及已规划前缀，例如两个人已经攻击某个目标，第三个人是否应该转火或治疗。

联合策略为 `π(A|O,H) = ∏ π(a_i|O,H,a_1…a_(i-1))`。这是同一个集中式模型输出整队计划，不是独立队员策略。规划顺序不是服务端出手顺序；伤害、先后手仍由引擎结算。初版使用固定的己方槽位/人物宠物顺序，并通过合法换边、编号重映射验收不受账号 ID 影响。

训练时采样，默认实战使用条件贪心；窄束搜索是后续可测选项，不能把策略概率当胜率。若增加完整计划价值评分，必须单独训练并验证，不能沿用当前“部分计划的最终胜负分数”假定。

规划完成后统一验证并顺序提交。游戏接口不提供整队原子提交：记录每条提交状态，已写入/未知结果不重复发，失效观察重新核对。人物换宠和本回合宠物行动等相互依赖需按原生规则专项核验，不能在规划阶段凭空生成新候选。

历史状态每个真实决策回合推进一次，同回合轮询和候选打分不重复推进。重连从保存事件重建；存在缺口则标记历史不完整并使用经过训练的缺失路径或显式回退，不伪造完整记忆。

## 训练环境：真实引擎，两条用途不同的路径

### 高速环境

扩展当前离线 C 入口，通过进程管道提供有版本的 `reset(scenario, seed)`、`observe(side)`、`step(joint_actions_of_both_sides)`、`close`。这些是本地实验接口，不开放到游戏服网络或管理端。

- 两方先分别获得同一决策时点的可见观察、产生计划，再进入统一结算；不得让后一方看到前一方的本回合选择。
- 引擎输出实际客户端观察报文及明确终局，Go 使用现有协议解析器、状态投影和候选构造；引擎完整内部状态只用于隔离实验标签/诊断，不交给策略或价值网络。
- 原生引擎若需要多次内部循环才能到达决策点，adapter 推进到真正边界，不假定一次 `BATTLE_Loop` 就是一回合。
- 人物/宠物/装备及竞技场临时资源规则复用现用逻辑；先建立状态和技能效果的差分测试，再扩大采集量。
- 每个 worker 独立进程，隔离旧引擎全局状态；长生命周期复用表加载，逐场清理。随机种子、架构、引擎/表摘要、初始条件全部记录；不宣称跨架构逐位复现。
- Mac 编排和学习器原生 Go；Linux 引擎使用经过发布的训练镜像/工具包。提供 `--data-dir` 和可选 Docker volume，正式使用不依赖仓库或 `build/local-arena`。ARM64 工具是否可可靠发布需先验证，必要时明确标记 amd64 仿真及性能代价。

### 完整链路环境

保留 `sactl ai simulate` 的账号服→游戏服→网关→客户端路径，用于检查登录、组队、匹配、回合截止时间、提交及资源恢复。扩展为双方策略/模型、配点场景、换边和固定对手池可配置。

高速环境负责大部分训练；完整链路是模型晋级必过的验收。直接裸 PVP 与竞技场可能有资源、起始状态或特殊规则差异，在一致性通过前不能把裸 PVP 成绩当作竞技场成绩。

## 训练方法：模仿热身 + PPO 自我对战

### 热身

用 basic、集火、保命/治疗、扰动探索等固定基线采集。规则策略只负责初始探索和比较，不把“赢家所有动作”都当正确标签。行为克隆学习基本有效操作，之后由对战结果改进。规则策略的实际动作需受候选和观察约束。

旧 10,000 场数据主要用于配点评估和引擎回归。若保留了完整、可转换的逐回合观察/动作，可另外用于有明确局限的热身；不能恢复候选集就不冒充现代策略轨迹。PVE 可以单独用于效果表示辅助训练，不作为竞技场胜负标签。

### PPO 主训练

- 一次环境动作是一个完整队伍计划，一次训练步是一个实际战斗决策回合。终局胜 +1、负 -1；引擎定义的真正平局 0。初版不添加伤害、拖延或存活奖励，避免偏离取胜目标。
- 对有限战斗先采用不额外偏好快赢/慢输的回报定义，初始 `gamma=1`，GAE 的 lambda 等参数再通过验证集调整。
- 策略使用采样时的候选 mask、规划顺序、每条条件 log-prob；联合 log-prob 为各项之和。PPO 以整队联合概率比优化，不能把各成员当独立环境。人数增加时检查 KL、裁剪比例与联合概率方差，必要时降低学习率或更新轮数。
- 价值头只读行动前允许可见的观察/历史，估计相同目标的回报；不使用敌方隐藏信息或刚选出的动作。初始模型不把该值宣传为已校准的获胜概率。
- recurrent PPO 按连续轨迹训练，用 burn-in 从同模型历史恢复状态，采用截断反向传播；不把回合任意打散后丢失记忆语义。已冻结的采集策略与优化策略分开保存。
- 每次尝试更新后重放完整历史，检查相对采集策略的整队近似 KL；超限则从该次更新前的权重和 Adam 状态减步重试，不能仅在下一次更新前停止却留下过大的上一更新。经验 KL 只限制采样分布上的平均变化，行为保留和胜率仍单独评测。
- `terminated` 与 `truncated` 分开：真实比赛回合上限按服务端结果处理；仅训练采集长度截断且有可靠后续状态时才 bootstrap；断线、丢事件、未知执行结果默认排除并计数。不得统一把超时标成败局/平局。
- 旧真人/LLM/历史模型日志不直接加入当前 PPO 更新。它们用于模仿、单独的辅助学习或评估；PPO 主批次来自冻结的当前行为策略，保存旧概率与 mask。

建议最初尝试每批 2,048～8,192 个队伍回合、少量更新轮数、KL 提前停止、熵正则和梯度裁剪；这是待测起始配置，不是效果承诺。批次不足就明确报告，不靠重复少数对局凑训练量。

### 对手池与持续迭代

初始对手采样可从固定规则 30%、冻结历史模型 50%、同代冻结模型 20% 起步。维护相互对战矩阵，补充能击败当前模型的历史对手，避免只会克制 basic，也避免简单 Elo 掩盖循环克制。

每轮流程：冻结采集模型与对手池 → 收集一批 → 训练候选 → 验证 → 晋级或保留旧版。生产对战每场固定模型，比赛中不改权重；可以后台训练，完成后下一场再选已批准的模型版本。

## 配点模块：build-search-v1

第一版不直接训练一个输出四个小数再四舍五入的网络。推荐“合法整数候选生成 + 小型配点评分模型 + 原生对战复验”。

- 严格遵守四项下限、上限、整数预算总和；多人阶段默认每个角色同预算，不擅自改成队内可任意转移总点数。
- 搜索器采用离散交叉熵搜索/整数局部移动，保留均衡、偏科和随机候选。评分模型用小型 MLP（初始两层 64）评价配置在指定场景、冻结战斗策略和对手分布下的预期成绩；精英候选必须回到真实引擎复验，限制模型误差被搜索放大。
- 配点决策只能使用开战前允许知道的信息。旧数据中对手完整配点是实验条件；正式匹配前不知道对手配点时，对公开对手分布求期望，不能在线偷用它。
- 用不同种子重复、双方换边评估，保留不确定性和多个互补方案；不宣称存在一套克制所有对手的万能配点。
- 先冻结战斗策略优化配点，再冻结一个多样配点池训练作战，最后交替迭代。每次配点成绩绑定战斗策略版本，避免模型变化导致旧排名失效而仍被使用。
- 线上第一版只给建议和预期适用条件。现有角色的未分配点数操作与不可逆成长，须遵守实际游戏能力和用户授权，不由训练器自行改动。

## 数据与产物

保留现有 SQLite 作为在线事件/执行事实来源，生产 battle records 作为可选补充；训练统一导出为有版本的对局分片与 manifest，Go 导入器兼容旧 JSONL/SQLite。运行时恢复日志与训练数据不混写；长期数据支持目录或 Docker volume，压缩完成的分片，不覆盖进行中的记录。

每局至少记录：规则和场景摘要、初始条件、种子/平台、双方策略和模型版本、预算定义、换边/重复组、完整性、权威终局。每步记录：可见观察、候选/掩码、历史截点、完整计划、实际提交/执行状态、采样概率、旧价值、后续观察、reward、terminated/truncated、回退原因。提议动作与实际执行动作分开，不把写入成功伪装成技能生效。

算法数据与原始日志必须能追溯。规则摘要覆盖 C 引擎、数据表、有效战斗参数及 adapter；协议兼容号单独保留。模型 manifest 保存网络/特征/动作 schema、认证模式和场景、训练数据摘要、超参数、种子、评估报告、权重校验值。训练 checkpoint 另外保存优化器、归一化、随机状态和对手池，区别于只含推理所需内容的发布模型。

旧线性模型继续按 v1 读取；新模型 schema v2 显式加载，不能默默重解释旧权重。保留 learned 策略 ID。模式/规则不兼容在排队前拒绝；场内未覆盖情形按配置回退并计数。hybrid 复用相同 Plan，附上候选概率/价值等有定义的诊断，不输出虚构的“胜率 99%”。

数据划分以实验家族为单位：同一配置对的重复、换边、双方视角、全部回合归一组；评估必须去除训练重叠。真人日志另外考虑角色/阵容重叠。划分 seed 不够，初始配置和对手策略也要有未见组合。训练集拟合归一化，验证集调参，最终测试集不用于选模型。

## 胜率验收与本机规模

| 验收 | 证据 |
| --- | --- |
| 协议/环境正确 | 高速与完整链路的同场景观察、动作效果、胜负、竞技资源恢复一致；未知字段显式保留 |
| 模型数值正确 | 算子梯度检查、保存加载一致、恢复训练、无 NaN/Inf、候选 mask 和同回合记忆不重复更新 |
| 决策时效 | 测 1v1/5v5 推理 p50/p95、截止时间内完成率、回退率；保留提交时间余量 |
| 策略效果 | 对 basic、固定规则池、上个冠军分别报告胜/负/平/截断、每场回合和置信区间；按模式/场景分层 |
| 泛化 | 新配点、宠物/装备组合、换边、未见对手；缺失信息和重连场景 |
| 晋级 | 预先冻结评测配置；对主要基线有统计支持的提升、对旧冠军达到预设非劣界限、无执行正确性回归 |

建议最终比较至少先安排约 1,000 场正常完成对局，再按测得差异和置信区间决定是否扩样；不是固定 1,000 场一定足够。换边/相同配置/随机种子重复具有相关性，置信区间按实验组做 cluster bootstrap；自我对战池用胜负矩阵辅助分析。共享种子可以降低部分比较噪声，但不同动作会改变 RNG 消耗，不承诺严格相同随机事件。

场地换边与算法所控制的配点归属需要独立平衡：每个家族两 seed × 两种配点归属 × 左右场地，共八场，统一作为一个统计组。新实验、训练、评估与晋级已接入 `pairing=roster-side-v1`，以新 schema 拒绝旧程序误读；旧四场赛程按原格式继续恢复和核验。相同规则对战的诊断已显示有限家族的配点强弱会显著影响绝对得分，详见实现记录。配点搜索则固定待评分阵容，仍按其原四场目标计分。

初始资源计划：先 2 个引擎 worker、1 个学习进程；跑 200～500 场短基准，测局/秒、回合/秒、峰值内存、记录体积和训练更新时间，再预算 10,000 场。先不启动无限采集，也不承诺一晚能训练到什么水平。默认 CPU，可中断并恢复，worker 数和磁盘保留量可配置。

完整训练成本含：Go 数值内核和梯度验证、可交互引擎 adapter、数据格式迁移、模型训练、真实链路评测；其中引擎一致性和动作语义完整性是先决条件，不能用扩大模型掩盖。

## 实施阶段与讨论建议

| 阶段 | 交付 | 进入下一阶段的门槛 |
| --- | --- | --- |
| A：环境与数据 | 逐回合 adapter、字段/候选审计、规则摘要、统一导出、性能基准 | 裸人物 1v1 的高速/真实链路一致，数据可重现和分组 |
| B：首个可学习模型 | 小网络、梯度校验、模仿/PPO、配点搜索、对手池、报告 | 同点数基准有独立对战证据；不是只有训练 loss 下降 |
| C：有实际策略空间的 1v1 | 人物+宠物，逐步加入治疗、状态、换宠和装备/道具 | 分场景优于基线，模型能力范围准确标注 |
| D：多人指挥 | 2v2 起训练，逐步覆盖 3v3～5v5，混合保留已学场景 | 每个模式独立验收；统一指挥胜过同等信息的独立决策对照 |
| E：正式本地产品 | 无仓库依赖的训练工具包、目录/volume、模型晋级/回退、帮助及 skill | Mac 安装与完整比赛验收，下载产物一致 |

建议把裸人物 1v1 作为环境及配点回归，把“人物+宠物的 1v1”作为首个有实用价值的 learned 目标。只有攻击/防御的裸人物场景可能很快到达策略上限，不应靠扩大网络或训练场次制造进步假象。

需要讨论的产品取舍：首个正式训练场景的宠物/装备/道具范围；是否以后新增严格同点数的游戏赛制；可接受的 Mac CPU/磁盘训练预算。当前推荐先保持游戏规则，固定一组可解释场景，再逐步放宽。
