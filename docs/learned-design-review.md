# learned 架构与训练讨论稿

日期：2026-09-30。本文用于讨论方案；完整技术设计见 [learned-strategy-design.md](learned-strategy-design.md)，原型证据见 [learned-implementation.md](learned-implementation.md)。设计目标、代码存在和效果验收是三件不同的事。

## 推荐方案

本地运行一个小型队伍指挥模型，Go 负责训练和推理，现用 C 战斗引擎负责结算。入口维持 `sactl ai`，保留 basic、learned、llm、hybrid。learned 独立工作不需要大模型 API；hybrid 再把其建议交给可配置的 Chat Completions 服务。

拆成两个相互配合的问题：

- 配点：在每个人物、宠物分别固定的合法整数预算内，搜索对指定对手分布有效的配置。
- 作战：配点确定后，根据全队观察和历史，输出这一回合的全队计划。

先固定作战模型搜索配点，再固定多样配点池训练作战，交替进行。每份配点结论绑定规则、作战模型和评估对手，避免把某个版本的最优解当成永久最优解。

正式竞技场的 power 匹配不是严格同点数比赛。首轮公平实验在本地受控环境进行；模型不会为实验自动修改线上人物属性。

## 模型架构

| 模块 | 推荐规格 | 解决的问题 |
| --- | --- | --- |
| 实体编码 | 两层 MLP，宽度 64 | 编码人物、宠物、属性和信息缺失标记 |
| 战场关系 | 两层、四头注意力，宽度 64 | 关联队友、敌人、主人与宠物 |
| 历史记忆 | GRU，宽度 64 | 按发生顺序处理攻击、恢复、控制等公开效果 |
| 联合计划 | 计划 GRU + 候选动作评分 | 后续安排能看到本回合已经计划的队友动作 |
| 价值头 | 小型 MLP | 训练时估计行动前局面的预期回报 |

当前默认原型约 20 万参数。先以 CPU 为目标，不要求用户安装 Python 或 GPU 环境；实际训练吞吐和整回合延迟需要在 Mac 测量。

一个队伍只有一个决策者。它可以依次规划“甲攻击目标 A、乙攻击目标 A、丙保护队友”，但所有选择共享全队观察和计划记忆。成员客户端只提交分配到自己的指令。规划顺序不代表实际出手顺序，速度和效果仍由引擎决定。

输入包括己方共享信息、敌方公开信息、合法动作及截至当前回合的历史。缺失数据明确标记，不把未知当成零；不使用敌方隐藏属性或尚未公开的当回合指令。账号、名字不作为学习特征。

网络可以表示 1v1～5v5，不代表 1v1 训练后便有多人能力。每个人数模式分别训练、评估和声明适用范围。

## 训练路线

1. **环境与动作校验。** 同一场景通过原生训练接口和完整客户端链路检查观察、实际技能效果、胜负及资源恢复。先保证模型能控制真实动作。
2. **模仿热身。** 从合法规则策略获得初始行为，避免模型一开始完全随机。不能把赢家的每个动作都标为最优。
3. **循环采集与 PPO。** 冻结本批采集模型，收集完整队伍轨迹，训练候选模型，再独立验证。每个学习动作是整队计划；历史按序训练，不把队员或回合随机拆开当成独立样本。
4. **多样对手。** 同时对战固定规则、历史模型和同代冻结模型，逐步补充能克制当前模型的对手。已有对手池、受控原生冠军挑战入口和逐场冠军选择/恢复实现；真实合格冠军的联网选择与完整竞技场认证仍须完成。
5. **配点交替优化。** 合法整数搜索产生候选，小型评分器筛选，实际引擎复验，再把多样配置用于下一轮作战训练。

推荐按批交替采集和训练，比赛内权重保持不变。后台可以训练，候选通过评估后再供新比赛使用。无需等积攒全部数据才开始学习，也不在每回合后立即替换线上权重。

初始奖励为胜 +1、负 -1、真实平局 0；不先加入伤害或存活奖励，避免模型追求刷伤害、拖回合。采集截断、断线和真正终局分开处理。旧日志可用于热身、分析或评估；缺少行为概率、候选集和观察截点的数据不能直接冒充当前 PPO 样本。

当前代码的 PPO 起始参数为学习率 3e-4、每批 3 轮更新、概率比裁剪 0.2、gamma=1、GAE lambda=0.95、历史反向传播片段 16 回合、熵系数 0.01、梯度裁剪 0.5、目标 KL 0.03。它们是实验起点，不是已经找到的最佳配置。每轮以整队联合动作概率计算更新；重新计算连续历史，保留记忆，片段边界仅截断梯度。单模式训练路径仍拒绝混入其他人数模式。另有显式的 `experiment-mix`、`train --mixed-experiment` 路径：冻结各模式的完整配点家族和采样配额，按模式归一化优势、加权队伍回合目标，共用一个模型和 Adam，并分别检查各模式的 KL。混合路径目前仅支持 PPO，不支持混合模仿热身；可从保留来源的父模型开始。多模式导出、逐模式评估和所有模式共同通过的冠军门槛已有功能验证，共享模型的实际强度、原有模式能力保留和协同优势仍需独立比赛证明，见 [训练说明](learned-training.md)。

配点搜索首轮固定等级、装备、宠物池和每个角色的预算，生成合法整数分配；评分模型先筛选，候选必须回到原生引擎对战。冻结作战策略时才能比较配点，更新作战策略后重新验证配点排名。不能把固定攻击策略下的最优配点当作所有作战策略下的最优配点。

## 数据和验收

每场保存规则摘要、初始条件、预算、种子、双方模型、配置分组和终局；每回合保存可见观察、有序事件、候选集、完整计划、选择概率、实际执行结果和下一观察。数据支持目录或 Docker volume，原始轨迹、训练 checkpoint 与推理模型分别保留。

训练、验证、最终测试按配置家族分组。同场双方视角、重复和换边必须在同一组，避免同一场景同时出现在训练和测试中。还需测试未见配点、宠物组合和对手策略。

以独立比赛胜率、置信区间、截止时间内完成率、回退率验收，不以 loss 下降或少数胜局验收。先测 200～500 场的吞吐、内存和数据体积，再安排大规模训练。最终比较建议从约 1,000 场开始，按独立组数量和统计不确定性决定是否扩样；场数本身不是强度保证。

## 当前核查发现与前置门槛

本讨论稿本次复核了模型、PPO、指挥官观察校验代码及既有设计/实现记录；没有重新运行训练或测试。下述结果来自先前记录，不表示本次新增验证。

`build/learned/status-actions-effect-test.log` 中，原生环境返回七个宠物技能，但公共观察的 `BattlePetSlotKnown=false`，候选只有宠物等待。另一个原生 fixture 问题是宠物技能槽容量为零；当前 C 源码已设置容量，出战宠物观察问题随后通过实际 `S(AI)` 的可选 `active_pet` 字段修复，Web、sactl 和离线 replay 共用该来源。

因此，既有微型训练和链路成功记录只能证明其中已验证的机制，不能证明宠物战术有效，更不能证明模型稳定强于基线。修复后，真实原生测试已确认四种状态攻击实际产生 BM 效果，并重新验证 30 组训练/竞技场差分；没有给学习器直接填入隐藏引擎状态。新采集、训练和完整链路的范围见实现记录。修正后的规则和动作版本须重新采集、训练及评估，旧结果保留原标签。

受控单体/群体治疗、小块肉、多宠切换、公共反射/保护承伤者及忠犬攻击已逐步接入，见实现记录。其他魔法/道具与特殊技能、完整多人强度、真实合格冠军联网验证和独立工具包的正式发布仍有未完成项；已有候选不能作为强策略发布。

已有 lambda、动作采样和熵系数对照尚未证明相对父模型有可靠、全面的胜率提升。基础实现正确性、实际指令可执行和战术强度必须分别验收。后续先检查行为覆盖、奖励归因、更新幅度和跨训练种子稳定性，再决定调参或更换学习方法；不能只加场数、加参数，或降低晋级门槛。最终测试集保持独立，开发用验证结果不能作为最终认证。

四种策略继续使用统一的队伍观察和完整 Plan 契约：basic 提供默认合法选择，learned 本地推理，llm 使用可配置 Chat Completions 生成结构化计划，hybrid 把 learned 建议连同观察/历史交给大模型作最终判断。动作都经过相同校验与截止时间控制。策略异常按显式配置处理并记录回退；回退获胜不能记为 learned 正常决策的胜率证据。

## 建议讨论的产品范围

推荐首个可用目标为“同点数人物 + 宠物的 1v1”：固定等级和装备条件，先覆盖攻击、防御、破防与状态技能，验证后加入治疗、换宠及道具。裸人物对战作为配点和环境回归；随后从 2v2 推进到 5v5，保留已有模式的回归评估。

主要取舍是首版先固定宠物与装备池，还是立即追求所有组合。推荐固定一个公开、可解释的场景池，尽早获得可信的胜率比较，再扩大覆盖。有限动作阶段应明确标记为实验模型，不宣称覆盖完整竞技场能力。
